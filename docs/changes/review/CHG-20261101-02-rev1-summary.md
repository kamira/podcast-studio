## 4. 跨 task 的共同問題

1. **分組繳交的實際覆蓋率遠低於草擬時的想像(R1S-2、R1S-5、R1S-9)**:CHG 與 diff 分開裝箱、每類至多 2 組,加上本專案 CHG 普遍超過 19000 字,Opus 席在多數 PR 只能看到 CHG 的一部分,判決幾乎都被合成為 concern。規則與實作一致、使用者已接受代價,但這會使 Opus 席的 concern 失去區辨力;合併 PR 與之後的統整席應把「僅因未送審而 concern」與「有實質發現的 concern」分開看(分組明細與 reason 的「(合成:有未送審的內容……)」可辨識)。
2. **施工判讀揭露不完整(R1S-3、R1S-4)**:R1-T1 施工者在 PR 說明與派發記錄誠實寫了 5 點判讀,但非 Python 檔不依 hunk 切的偏離沒有寫出,第 4 點的字數也無法重現。之後的施工判讀應附可重現的量測方式(哪個 commit、量的是字還是 bytes)。
3. **帳本狀態落後(R1S-15、R1S-18)**:與原 CHG DIR-5 統整報告 RS-16 同類,task 合入後表頭、派發記錄、狀態、後續改善未同步。
4. **本機 glm4 / qwen3 席無法審本類變更**:兩個 PR 的 impact、drift 都是 diff 截到 0 字;drift 兩次虛構分組標記與不存在的檔案和函式。合併 PR 預期同樣狀況,統整席應以程式與規格自行核對,不要把這些席的 concern 當成待修項。
